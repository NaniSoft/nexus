The factory is five components with narrow contracts between them.

| Component | Responsibility |
| --- | --- |
| **Config loader** | Reads and validates `factories/*.yaml`; exposes values to every other component. |
| **Issue poller** | Reads open issues from each configured repository; converts them to work items. |
| **Orchestrator + workers** | Accepts work items, starts worker containers, drives the build, tracks rounds. |
| **Kanban service** | Serves the board at port 5000. It holds no board state of its own. |
| **Merger** | Opens and merges the pull request when a ticket is approved. |

These are five components in **one .NET process**, not five services. The board
is an ASP.NET Core endpoint that same process serves, and the components call
each other as ordinary method calls.

## The path of a work item

1. The **config loader** starts first. Nothing else runs without a validated
   project configuration — see [the configuration model](/docs/configuration/the-configuration-model).
2. The **issue poller** reads open issues from each configured repository, in
   round-robin order. Each issue becomes a work item in **Backlog**.
3. Work items are **persisted** in SQLite, which is the store of record, so the
   board and the orchestrator read the same state rather than each keeping its
   own.
4. Nothing is built until a reviewer **accepts** a work item, which moves it to
   **Frontier**. Intake is indiscriminate by design; deciding what is worth
   building is a human's job, and the board is where it happens.
5. When a container is free the **orchestrator** starts a fresh worker container
   and drives the build through NOpenCode and OpenCode. The item moves to **In
   Progress**.
6. On completion the item moves to **Review**, with the diff, the round's own
   record, and its log on the card.
7. On approval the **merger** opens the pull request against the configured
   repository and merges it. The item moves to **Done** — and only if a merge
   actually landed.

## Where the contracts are

The seams are deliberately boring. The poller knows GitHub and work items; it
does not know about containers. The orchestrator knows work items and rounds; it
does not know how the board renders. The board reads state and writes decisions;
it does not build. The merger knows pull requests; it does not decide.

Three things cross the boundary and nothing else does: a **clock**, the **agent
seam** (one call is one round), and the **GitHub seam** (one call is one merge).
Those three are the entire surface the application has to the outside world
besides Docker.

That is what makes the factory **generic**. Adding a project is a configuration
file, because no component has to learn anything about a project to serve it.

## What is deliberately not here

There is no scheduler component, no per-project plugin system, and no second
queue beside the board. Round-robin ordering, the round ceiling, the container
budget and escalation all live in the orchestrator, where [the retry and
escalation policy](/docs/architecture/observability-and-error-handling) can be
reasoned about in one place.
