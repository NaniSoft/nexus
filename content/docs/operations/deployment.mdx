The factory deploys with **Docker Compose**. That choice is not nostalgic: the
factory's own product is Docker containers, so the environment it runs in is
one it already has to understand, and a Compose file describes the whole thing
in a form that can be read, diffed, and reviewed like any other file in a
repository.

```bash
docker compose up --build -d
```

The board is then at **http://127.0.0.1:5000**.

## One deployment, every project

A single factory deployment serves **every project configured in
`factories/`**. There is no per-project deployment to stand up, and no
per-project credentials beyond what each project's own configuration names.
Adding a repository to the factory is [adding a file to a
directory](/docs/configuration/the-factories-layout), not adding a service.

## What is running

The deployment brings up the factory's components together: the orchestrator
with its worker pool, the board publishing at **port 5000**, and the Docker
runtime they both start containers against.

Workers are **not** long-running members of the deployment. A worker container
exists for one round, starts on demand, and is removed when the round ends —
successfully, on failure, or on cancellation — see
[the worker-container lifecycle](/docs/architecture/worker-container-lifecycle).

Review workspaces are a second kind of container, spawned on demand from a card
and destroyed on a decision. They are the only thing in the deployment that
publishes a port at all, and it binds to loopback.

## Three volumes

| Volume | What it keeps |
| --- | --- |
| Project files | What the board's projects page writes and the loader reads. |
| Secrets | Credential values, one file per credential, read at use time so a rotation needs no restart. |
| Store | The SQLite store of record, with each round's lifted tree beside it. |

A round's tree is **kept** after the round, because the host has to be able to
reach the round's commit once the container that made it is gone — the host
pushes, and the container cannot.

## The machine-only limit

The board mapping is pinned to `127.0.0.1` **on purpose**. There is no login,
because there is no second machine to ask who you are; local access *is* the
authorisation, and the target repository's own branch protection is the backstop
that makes unattended merging a policy rather than an unbounded risk.

Reaching the board from anywhere else is a deliberate flip of two things — the
mapping, and a token check on the board's writes — never an accident.

## The daemon, named where it is accepted

The deployment mounts the host Docker socket, so worker and workspace containers
are **siblings** on the host daemon rather than children of the factory's own.

Rootless Docker is a requirement where the factory runs for real. Docker Desktop
reports no rootless marker, and this is the named, bounded deviation: worker
containers get no host mount, publish no port, run as an unprivileged user with
no supplementary group, and hold one scoped credential for one round — the
compensating controls the worker image enforces and its own smoke test proves.
[Rootless Docker](/docs/configuration/rootless-docker) is the longer version.

## Before it starts

The config loader validates every project file at start, and a file that does
not validate keeps its project out of the rotation rather than failing the
deployment. Configuration is read at start and does not hot reload, so **a
changed file means a restart**.

Checking that the set of projects the factory is actually serving matches what
you expect is the first thing to do after a config change. The board — grouped
by project — is where that check is visible, and it reports each project's intake
state separately: never polled, polled, or failing. An empty board is three
different facts and only one of them is "there is nothing to do".

Projects and credentials are added through the board's own `/Projects` page, and
that page says where a repository is chosen that adding one makes the factory
reach it.

## No upgrade story yet

There is no release to upgrade from and no migration to run. When there is, this
page grows the section; until then, documenting an upgrade path for software
that has no versions would be a claim about the future wearing an operations
manual's clothes.
