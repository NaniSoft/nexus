---
title: Secrets and token scopes
description: Credentials are referenced by name from project config — and the GitHub token never enters a worker container at all.
---

A factory that builds code needs write access to the repositories it builds for,
and credentials for the models that do the building. That is a large amount of
power in one process, and the design treats it that way.

## Names in config, values elsewhere

Project configuration **references** credentials by environment variable name; it
never contains them. That separation does two things. It keeps `factories/*.yaml`
reviewable in public without leaking anything. And it makes rotating a credential
an environment change, not an edit to every project file that mentions it.

```yaml
# The config names the variable; the environment holds the value.
keys:
  github: ATLAS_GITHUB_TOKEN
  llm: ATLAS_ANTHROPIC_API_KEY
```

There is a second home for values as well as the environment — a secrets
directory, one file per credential, the name **is** the file. It is read at use
time, so a rotation needs no restart, and it is written by the board's own
credentials form, which is **write-only**: the page shows whether a name has a
value and never shows what the value is.

## The asymmetry, which is the point

The two credentials are **not** treated alike, and the difference is structural
rather than a policy someone has to remember.

**The GitHub write token never enters a worker container.** It is read on the
**host**, by the merger, after the round's container is gone. So a confused,
injected or compromised agent has nothing that could push anywhere — and this is
not a convention: the component that builds a round's environment never even asks
the reader for that name, so it cannot hand the value over even by accident.

**The LLM key does go in**, because the agent cannot reach a provider without
one. It is scoped to one project, lives for the life of one container, and is
never logged. When the environment does not have it the round still runs and a
warning says so — refusing there would be the factory deciding for itself that
the agent needs a key, and the agent is the thing that knows.

The value never appears in a log line, a request body, or a URL. It goes into one
`Authorization` header per request and into the environment of the one `git
push` child. The *name* is logged, because a name is not a secret and it is what
an operator has to go and fix.

## Token scopes: the narrowest that works

Credentials are **scoped to the narrowest set that still works**, and the
factory's own needs set the floor. Its GitHub path is: read open issues, create
and merge a pull request. A token that can do that does not need to do much else,
and the difference between that token and an account-wide one is the difference
between a compromised factory that can touch configured repositories and one that
can touch everything the account can see.

Scope the token to **one repository**, not the organisation.

Model credentials are per project for the same reason worker images are: projects
differ, and a factory-wide credential is a single point of failure for every
repository it serves. Scoping per project means a leaked or over-broad credential
has a blast radius of one project, and revoking it does not stop the others.

## What the agent cannot see

Beyond credentials, a round holds nothing that reaches the factory's host: **no
host path is mounted, no inbound port is published**, and the agent's own
configuration is switched off, because a file in the tree it is building could
otherwise point the provider at an endpoint of its choosing — which is the
credential leaving for wherever the tree said.
