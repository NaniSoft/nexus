---
title: Secrets and token scopes
description: Secrets arrive as environment variables and are referenced by name from project config — with the narrowest scope that works.
---

A factory that builds code needs write access to the repositories it builds
for, and credentials for the models that do the building. That is a large
amount of power in one process, and the design treats it that way.

## Environment variables, not config files

Secrets are carried as **environment variables**. Project configuration
**references** them by name; it does not contain them.

That separation does two things. It keeps `factories/*.yaml` committable — a
project's configuration can be reviewed in the open without leaking anything.
And it means rotating a credential is an environment change, not an edit to
every project file that mentions it.

```yaml
# The config names the variable; the environment holds the value.
keys:
  github: GITHUB_TOKEN
  llm: LLM_API_KEY
```

## Token scopes: the narrowest that works

Credentials are **scoped to the narrowest set that still works**, and the
factory's own needs set the floor. Its GitHub path is: read open issues, create
and merge a pull request. A token that can do that does not need to do much
else, and the difference between that token and an account-wide one is the
difference between a compromised factory that can touch configured repositories
and one that can touch everything the account can see.

The same reasoning applies to model credentials: they authorise model calls, not
infrastructure, and they are per project in configuration so one project's
provider choice cannot become another project's bill.

## Why per-project keys matter

Keys are a **per-project** concern in configuration for the same reason worker
images are: projects differ, and a factory-wide credential is a single point of
failure for every repository it serves. Scoping per project means a leaked or
over-broad credential has a blast radius of one project, and revoking it does
not stop the others.

## In the container

The build agents inside a worker container receive the credentials their project
declares, scoped to that project, for the life of that container. The container
is [torn down](/docs/architecture/worker-container-lifecycle#the-stages) when
the run ends; the credentials' usability ends with it.
