title: Orchestration
description: A hand-rolled deterministic state machine that owns the factory's policy; OpenCode does the coding inside each worker container.
---

Orchestration is what turns a queue of work items into running builds. Nexus
orchestrates with a **deterministic state machine** and does the coding with
**OpenCode**.

## No agent framework in the loop

There is deliberately **no Microsoft Agent Framework** here, and the reason is
worth stating rather than leaving as an absence.

A framework would put host-side agents in the loop: objects with a runtime that
owns their concurrency, handoff, and failure. This factory has no host-side
agents. Every decision the factory makes is a state transition over a work item
in a store, and every one of them is decided by the same code path whether a
container was started, a reviewer's click arrived, or a heartbeat asked the
machine to look again. An agent in that position would make the factory's
behaviour depend on a model's judgement about what to do next — and the whole
guarantee the design makes is that a reviewer knows what the factory will do.

So the orchestrator is a hand-rolled state machine, stepped rather than driven.
One step applies at most one transition. Nothing sleeps, defers, or times out
in the loop: the 90-minute round timeout is a comparison against an injectable
clock rather than a timer, which is what makes it testable at all.

## One process, ordinary method calls

The orchestrator is part of a single .NET process. The config loader, the issue
poller, the container runtime, the Kanban board, and the merger all sit in the
same runtime, which is what makes their contracts ordinary method calls rather
than network guesses.

## The agent seam

The orchestrator does not reach into a container to run commands. It hands a
work item to **`NOpenCode`** — one call is one round — and `NOpenCode` drives
**OpenCode** inside the worker container and returns a result. What came back is
derived by *observing* the container, not by believing the agent: files changed
from git, commands from a recording wrapper, outcomes from exit codes.

The orchestrator consumes those results and updates the work item. It never
learns what a container is.

That boundary is deliberate. The orchestrator knows about work items, rounds,
and pull requests. OpenCode knows about repositories and code. Neither needs to
model the other's internals, which is what lets either side change without the
other following.

## What the orchestrator decides

Given a work item, the orchestrator decides the things a factory has to decide
the same way every time:

- which project's configuration applies;
- when a worker container starts, and what happens when it exits;
- whether the result goes to Review, back to the build, or to escalation;
- when the round counter closes the loop.

Those decisions are the factory's actual policy. They are written down in
[Architecture — orchestration layer](/docs/architecture/orchestration-layer).

## What it holds no opinion about

Factory behaviour — the round ceiling, the timeouts, the merge policy, the retry
strategy — is **code, not configuration**. Identical for every project. The one
deliberate exception is auto-merge, which is a factory-level setting with a
default of **off**, so a work item waits in Review until a human decides unless
an operator turns the timeout on deliberately.
